🧙 Kreator konfiguracji

Pierwsza konfiguracja bridge'a Satel-Tuya-eBUS - podzielona na etapy. Po każdym kliknięciu Dalej postęp zapisuje się automatycznie na serwerze, więc kreator da się bezpiecznie przerwać i wrócić do niego później (nawet z innego urządzenia w tej samej sieci). To, czego kreator nie obsługuje (reguły kamer, alarmy progowe, automatyka kotła), da się dopisać ręcznie w config.yaml albo przez panel po zapisie.
🐛 Debug - komunikacja sieciowa dla akcji w tym kroku (testy połączenia, wykrywanie, import, zapis). Hasła/klucze/sekrety zawsze ukryte.
Brak zdarzeń jeszcze - wykonaj jakąś akcję (np. "Testuj połączenie").
↻ Wznowiono zapisany wcześniej postęp kreatora.
1
Centrala Satel Integra
Dane z konfiguracji ETHM-1 Plus w programie DLOADX.
Sprawdza tylko, czy pod tym adresem/portem coś odpowiada (TCP) - protokół integracji Satela nie pozwala zweryfikować samego klucza bez wykonania polecenia zmieniającego stan (uzbrojenie/wyjście), więc test świadomie tego nie robi. Błędny klucz ujawni się dopiero przy pierwszym uzbrojeniu/rozbrojeniu.
⚠ To hasło protokołu integracji, nie klucz szyfrowania. Ten bridge (biblioteka satel_integra) nie obsługuje opcjonalnego szyfrowania AES transmisji TCP, jakie oferują niektóre centrale/moduły ETHM - komunikacja z centralą idzie czystym tekstem po sieci LAN. Jeśli panel/bridge ma być dostępny spoza zaufanej sieci domowej, użyj VPN (WireGuard/Tailscale) albo izolowanego VLAN-u zamiast wystawiać port na świat. Szczegóły w README, sekcja "Bezpieczeństwo".
Protokół integracji Satela NIE udostępnia pełnej listy skonfigurowanych stref/wyjść wraz z nazwami (ograniczenie protokołu, nie dało się tego obejść) - to, co REALNIE można zrobić: nasłuchiwać przez 30 sekund i zanotować numery, które w tym czasie ZMIENIĄ STAN. Podczas nasłuchu przejdź przez pilnowane pomieszczenia (otwórz/zamknij drzwi i okna, wywołaj czujki ruchu) - wykryte numery trafią jako nowe wiersze niżej (dopisz im nazwy). Strefy, które nie zmienią stanu w tym oknie, nie zostaną wykryte - dodaj je ręcznie, jeśli znasz ich numer z DLOADX. Nie wymaga klucza integracji (jak "Testuj połączenie" wyżej).
2
Urządzenia Tuya
Trzy sposoby dodania urządzeń poniżej - można je łączyć, wszystkie trafiają na tę samą listę na dole. Przy wielu urządzeniach polecamy import z Tuya Cloud - jedno pobranie zamiast ręcznego wpisywania każdego z osobna (dokładnie to samo, co robi tinytuya wizard, tylko bez konsoli).
Local key każdego urządzenia wyciągasz narzędziem tinytuya wizard z terminala (wymaga jednorazowego zalogowania do konta Tuya) - albo skanem sieci niżej, który podpowie ID i adres IP (ale NIE local_key - Tuya świadomie go nie rozgłasza).
↗ Otwórz instrukcję tinytuya wizard
Wymaga projektu w Tuya IoT Platform z podpiętą aplikacją (Tuya Smart / Smart Life) - gdzie znaleźć Access ID/Secret i jak założyć projekt, jeśli go nie masz, patrz krok 7 ("Integracje opcjonalne"). Te same dane wykorzystasz też do integracji kamer Tuya Cloud w kroku 7 - wpisane tu, przenoszą się tam automatycznie (i odwrotnie), nie trzeba wpisywać ich dwa razy.
3
eBUS / ebusd (kocioł)
Broker MQTT, na który publikuje ebusd. Same czujniki kotła dodasz po zapisaniu, w zakładce "Ustawienia czujników".
Bridge sam NIE instaluje/uruchamia usług systemowych (wymagałoby to uprawnień administratora RPi z poziomu przeglądarki - świadomie tego unikamy). Adres skonfigurowany na 127.0.0.1:1883 - zanim uruchomisz bridge'a, uruchom broker jedną z dwóch metod: 
sudo apt update && sudo apt install -y mosquitto
sudo systemctl enable --now mosquitto
...albo, jeśli używasz Dockera (patrz README, sekcja "Uruchomienie w Dockerze"): 
docker compose --profile broker up -d mosquitto
Sam ebusd (fizyczne podłączenie do magistrali eBUS kotła) trzeba skonfigurować osobno niezależnie od tego wyboru - patrz README, sekcja "eBUS / ebusd".

7
Integracje opcjonalne
↗ Otwórz developer.tuya.com
Gdzie znaleźć Access ID / Access Secret: developer.tuya.com → zaloguj się → Cloud (menu boczne) → wybierz swój projekt z listy → zakładka Overview pokazuje Access ID/Client ID oraz Access Secret/Client Secret (kliknij "Show" przy Secret).

Nie masz jeszcze projektu? Załóż go raz (te same poświadczenia wykorzystasz też w kroku 2 do importu urządzeń - pola niżej i w kroku 2 są zsynchronizowane, wpisz je tylko raz w którymkolwiek miejscu):
  1. Zarejestruj się/zaloguj na developer.tuya.com (darmowe konto).
  2. Cloud → Create Cloud Project - dowolna nazwa, region jak najbliższy Tobie (np. Europa Centralna), typ "Smart Home PaaS" albo "Smart Home Basic Edition".
  3. Po utworzeniu projektu: zakładka Devices → Link Tuya App Account - zeskanuj kod QR aplikacją Tuya Smart/Smart Life (tą samą, w której masz już dodane swoje urządzenia) - to podpina Twoje realne urządzenia pod projekt chmurowy.
  4. Zakładka Service API - upewnij się, że włączone są co najmniej "IoT Core" i "Authorization" (zwykle domyślnie tak).
  5. Wróć do zakładki Overview po Access ID/Secret.
8
Sceny (zaawansowane)
Nazwana grupa akcji na wielu urządzeniach naraz, wywoływana jednym zdarzeniem (np. "wykryto_intruza" włącza światła i wywołuje wirtualne wejście). Sceny zdefiniowane tutaj będzie można wybrać w kolejnym kroku ("Reguły ruchu") jako akcję albo jako cel eskalacji.
9
Reguły ruchu: harmonogramy i eskalacja
Naruszenie wejścia Satela → włącz urządzenie na czas (albo uruchom scenę). Opcjonalnie: harmonogram - reguła aktywna tylko w wybranych godzinach, oraz eskalacja - kilka naruszeń w krótkim czasie wywołuje mocniejszą scenę zamiast zwykłej akcji. (Reguły dla ruchu z czujek Tuya PIR i reguły kamer da się dodać tylko ręcznie w config.yaml - patrz README.)
10
Podsumowanie
Sprawdź poniżej, zanim zapiszesz - po zapisie kreator się blokuje (patrz nagłówek wygenerowanego config.yaml).
Żeby to wszystko uruchamiało się automatycznie po restarcie RPi (zamiast ręcznie odpalać za każdym razem) - zrób to PO zapisaniu, jedną z dwóch metod:

A) usługi systemd (dwa pliki - bridge i panel): 
sudo tee /etc/systemd/system/satel-tuya-bridge.service >/dev/null <<'EOF'
[Unit]
Description=Satel-Tuya-eBUS bridge
After=network-online.target
[Service]
Type=simple
User=pi
WorkingDirectory=/home/pi/satel_tuya_bridge
ExecStart=/home/pi/satel_tuya_bridge/venv/bin/python main.py
Restart=on-failure
RestartSec=5
[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now satel-tuya-bridge
...analogicznie drugi plik dla panelu (satel-tuya-dashboard.service, ExecStart=... python -m dashboard.app --config config.yaml --port 8090). Dopasuj ścieżki (WorkingDirectory/ExecStart) do swojej instalacji. Pełny opis - README, sekcja "Uruchomienie jako usługa systemd".

B) Docker (jeśli tak wdrażasz - patrz README, sekcja "Uruchomienie w Dockerze"): 
docker compose up -d
restart po awarii/reboot już wbudowany (restart: unless-stopped w docker-compose.yml).
